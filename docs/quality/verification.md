# 변경 검증과 결과 기록

[테스트·품질 목차](index.md) · 관련: [위키와 프로젝트의 상호 반영](../baseline.md#위키와-프로젝트의-상호-반영), [RnimanEngine](../projects/rniman-engine.md)

상태: 초안 · 적용 범위: 개인 프로젝트의 변경 검증·완료 보고 · 제안일: 2026-09-15

검증 범위는 변경으로 달라지는 동작에 맞춘다. 아래 강도는 채택 시의 제안이며 모든 변경에 동일한 테스트 도구나 실행 환경을 요구하지 않는다.

## 규칙과 예외

| 항목 | 제안 기준 | 강도 | 이유·조건 |
| --- | --- | --- | --- |
| 빌드 | 영향받는 타깃과 지원 구성을 확인하고 결과 기록 | 필수 | 컴파일·링크 문제를 확인. 문서만 수정한 경우 내용·링크와 필요한 문서 빌드로 대체 |
| 실행 | 달라진 사용자 흐름의 실행·종료·오류 동작 확인 | 필수 | 빌드만으로 동작을 보장할 수 없음. 라이브러리는 테스트나 소비 앱으로 확인 |
| 화면 | 표시 결과가 핵심이면 기대 결과와 실제 화면 비교 | 필수 | 프로세스 생존·창 핸들 확인과 화면 정확성을 구분 |
| 공통 코드 | 영향받는 유지 샘플과 대표 사용 경로 확인 | 권장 | 통합 회귀를 발견. 과거 버전 보존 샘플은 유지 대상과 구분 |
| 오류·수명 | 부분 실패 정리, 잘못된 입력, 무효화 조건을 우선 검증 | 권장 | 정상 경로에서 드러나지 않는 결함 확인 |
| 미실행 항목 | 실행하지 못한 검증과 이유 기록 | 필수 | 다른 사람의 기록과 이번 직접 검증을 구분 |
| 성능 | 조건·대상·단위·측정 구간을 기록하고 비교 | 필수 | 측정 없이 향상을 단정하지 않음 |

독립 로직의 반복 가능한 검증에는 자동 테스트를 권장한다. 파일 파서는 잘린 입력·미지원 버전·범위·크기 계산 오버플로, 핸들 기반 저장소는 재사용·삭제 후 접근·순회 중 변경을 후보로 삼는다. 이 예시는 해당 기능이 있을 때 적용하며 ECS나 바이너리 형식을 모든 프로젝트에 요구하지 않는다.

GPU 자원 수명이나 렌더링 결과는 CPU 단위 테스트만으로 완료 처리하지 않는다. 프로젝트가 선택한 디버그 레이어·실행 확인으로 보완한다. 반대로 모든 변경에 GPU 실행이 필요한 것은 아니다.

## 결과 기록

검증 기록에는 대상 변경·환경·수행한 절차·기대 결과·실제 결과·미검증 항목을 남긴다. 과거 검증을 인용할 때는 출처와 수행 시점을 구분한다. 특정 프로젝트의 실제 결과는 해당 프로젝트 문서에서 관리한다.

성능 비교는 같은 입력·작업량·구성·측정 환경에서 수행하고 반복 횟수와 결과 요약을 남긴다. 캐시 최초 생성과 재사용, CPU 작업과 GPU 작업·대기, 파일 크기와 메모리 사용량은 각각의 지표로 기록한다. 구체적인 측정 도구·반복 횟수·허용 기준은 프로젝트가 정하며 ECS·PCH·캐시 도입 자체로 성능 향상을 확정하지 않는다.

## 근거와 변경 기록

- 2026-09-15: 프로젝트별 검증 결과를 프로젝트 문서로 통합하고 이 문서에는 공통 기록 기준만 남겼다. 초안 상태와 규칙 강도는 유지했다.

프로젝트 사례의 근거는 [RnimanEngine의 원본 안내](../projects/rniman-engine.md#공통-초안의-근거)을 참조한다. [과거 자료](../../ref/CodingConvention.md)의 테스트 가능성과 최적화 권고를 참고하되, 특정 구현을 빠르다고 가정하지 않고 조건·측정 결과로 판단하도록 정리했다. 외부 표준을 새로 채택한 문서가 아니다.

- 2026-09-15: 빌드·실행·화면·성능 검증을 구분하는 초안을 추가했다. 도구와 프로젝트별 통과 기준은 미결정이다.
